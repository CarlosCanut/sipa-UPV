## Workflow and data rules

1. Coordination creates competencies/forms, companies and accounts; completes or imports actor locations and capacities.
2. Companies create offers. Students rank offers and self-assess skills. Tutors confirm availability. A readiness summary points out incomplete inputs.
3. Coordination launches, compares and reviews simulations, then publishes one. Data edits affect future runs; solver input snapshots remain unchanged.
4. Participants see only their published assignments and can rate them. Each person can submit/update a pilot questionnaire. Coordination exports results for analysis.

CSV accepts at most 500 records / 500 KB. Student/tutor CSV updates existing accounts by email; account creation stays in Usuarios. Companies and offers update by id; blank id creates a new record. Imports validate again on commit and roll back completely on failure. Templates and current exports use the same schemas as forms. Boolean cells use `true`/`false`; coordinates use decimal points; offer requirements are JSON keyed by competency id. Catalog IDs are listed on the import screen. CSV exports escape formula-like text; do not remove this protection when sharing spreadsheets.

Offers use deactivation to preserve assignment history. Catalog entries can be deleted only when unused; an in-use form cannot change its competency membership. The published assignment links refer to current display names/contact details, while metrics and numerical comparisons use the saved input snapshot.

Feedback is scoped to the current publication and participant, with one editable rating per person/assignment. Questionnaire responses are identified, not anonymous; admin views group/display role and exports include respondent IDs. No external messaging or geocoding service is required.

## Metric interpretation

Student distance is Haversine, one-way, per assignment. Tutor travel estimates one one-way visit per distinct tutor/placement pair from snapshot coordinates; it is not a route plan or a recurring travel forecast. Comparison suppresses the travel-change claim when inputs or assigned students differ. Missing priority groups display “—” in comparison, not a successful equity result. Computation duration includes application/solver response overhead, not human decision time.

Before a real pilot: integrate and test the validated algorithm (including dependency, development, company preference and tutor objectives), agree on cases and success criteria with centers, establish a manual/current-method baseline, measure workflow time and real travel assumptions, collect user feedback, and document outcomes. Public HTTPS and official UPV branding also remain deployment/approval tasks.
